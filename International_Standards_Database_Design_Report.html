Introduction · The Problem

Why Standards Matter

Every unmanaged database project eventually collides with the same problem: the data it produces cannot easily speak to the data produced by anyone else. Standards are the contracts that prevent this failure.

A database without standards is a local success and a global liability. It works inside its own walls, but the moment another system needs to consume, merge, or audit it, hidden costs appear — schema mismatches, undocumented codes, inconsistent geometries, missing metadata. Standards exist to flatten that cost.

In spatial and enterprise contexts, five families of standards do most of the heavy lifting: INSPIRE for thematic harmonization, OGC for interoperability services, ISO for formal data modeling and quality, Esri for practical implementation patterns, and UML/OMG for the modeling language itself. This report shows how they fit together.

Fig 01 Without shared standards, every integration is a custom project. With standards, integration becomes a property of the system — not a task.
The Core Idea Standards convert integration from a project into a property. When two systems both follow the same standard, making them talk stops being engineering work and starts being a configuration detail.

The Five Pillars

Each pillar answers a different question. Together, they form a complete design system for enterprise and spatial databases.

i.
Content vs. Mechanics
INSPIRE and ISO define what and how well. OGC and Esri define how it moves and how it's implemented. UML is the shared language that lets all parties agree before anyone writes SQL.
ii.
Overlapping by Design
These pillars are complementary, not competing. A mature enterprise geodatabase uses all five simultaneously — ISO metadata, OGC publishing, INSPIRE-aligned schemas, Esri domains, and UML documentation.
iii.
Depth Over Breadth
You don't need to master every clause. Pick the 10 ISO and OGC standards that fit your domain, apply them rigorously, and document gaps. That beats shallow conformance to fifty.

Pillar One · European SDI

The INSPIRE Directive

INSPIRE (Infrastructure for Spatial Information in the European Community, Directive 2007/2/EC) is the most ambitious attempt ever made to harmonize spatial data across nations. Even outside Europe, its thematic model is a pragmatic blueprint.

INSPIRE's purpose is not to replace your database — it's to make your database speak a shared thematic language. If your country authority ships "Buildings" that conform to INSPIRE, another municipality — or another country — can consume them without a custom adapter.

What INSPIRE Defines

Table 3.1 — INSPIRE Core Components / Components
Component Definition Practical Impact
34 Data Themes Annex I, II, III topics covering everything from coordinate reference systems to energy resources. Gives you a known list of feature types to align your schema against.
Data Specifications Formal schema rules per theme — attribute names, data types, multiplicity, relationships. Tells you exactly which fields are mandatory, which are optional, and which are forbidden.
Code Lists Controlled vocabularies for categorical attributes (e.g., residential industrial agricultural). Eliminates free-text chaos. Enables automated join and validation.
Metadata Profile INSPIRE extension of ISO 19115 — mandatory elements for discovery and evaluation. Every dataset must ship with metadata compliant with the profile. No metadata = not INSPIRE.
Network Services Discovery (CSW), View (WMS), Download (WFS/Atom), Transformation, Invoke. The delivery mechanism. Standardizes how users find and access your data online.

The Three Annexes

Fig 02 The 34 INSPIRE themes are organized in three annexes reflecting priority and dependency — foundations first, reference data second, thematic layers built on top.
How to Apply When starting a new schema, map each proposed feature class to the closest INSPIRE theme. Even if you do not ship INSPIRE services, adopting the theme's attribute names and code lists will save you years of refactoring when your data eventually needs to cross borders.

Pillar Two · Interoperability

OGC Standards

The Open Geospatial Consortium writes the rules by which spatial systems talk to each other over the network. If INSPIRE defines the words, OGC defines the grammar of the conversation.

OGC standards cover two things: service interfaces (how software requests data) and data formats (the structure of what gets delivered). A modern design uses legacy OGC (WMS/WFS/WCS) for breadth of client support and the new OGC API family for any greenfield work.

Table 4.1 — OGC Service Standards / Services
Standard Full Name Purpose Replaces / Successor
WMS Web Map Service Returns rendered map images (PNG/JPEG) for display. Server-side styling. → OGC API – Maps
WMTS Web Map Tile Service Pre-rendered tiled maps for fast client-side zooming and panning. → OGC API – Tiles
WFS Web Feature Service Access to raw vector features with query and, with WFS-T, editing. → OGC API – Features
WCS Web Coverage Service Raster coverage access — DEMs, imagery, multi-band data. → OGC API – Coverages
WPS Web Processing Service Expose geoprocessing operations as HTTP endpoints. → OGC API – Processes
CSW Catalog Service for the Web Discovery of datasets and services via metadata queries. → OGC API – Records
SensorThings SensorThings API RESTful model for IoT and sensor observations. Purpose-built for streaming data. — Current standard —
Table 4.2 — OGC Data Format Standards / Formats
Format Best Suited For Design Notes
GML INSPIRE-compliant exchange, heavy-duty interoperability XML-based. Verbose but expressive. The canonical INSPIRE encoding. Use when maximum schema fidelity is required.
GeoJSON Web APIs, JavaScript clients, lightweight exchange JSON-based. Simple. Always WGS84 by default. Ideal for web-native workflows but limited attribute typing.

Modernization Note The OGC API family (Features, Tiles, Maps, Coverages, Processes, Records) is replacing the XML-based WxS generation. It uses JSON, HTTP, and OpenAPI — making geospatial services first-class citizens of modern API ecosystems. For any new infrastructure, design for OGC API first and expose legacy WxS as a compatibility layer.

Pillar Three · Foundation Layer

ISO Standards

ISO standards are the tectonic plates under everything else. INSPIRE extends them. OGC formalizes them as services. Esri implements them as product features. You rarely call out ISO directly, but ignoring it guarantees a brittle database.

The ISO 19100 Geospatial Series

Standard Title / Topic What It Governs

ISO 19107 Spatial schema Conceptual model for geometry (points, curves, surfaces, solids) and topology.
ISO 19108 Temporal schema Time concepts for geographic features — instants, periods, temporal topology.
ISO 19111 Coordinate referencing Rules for coordinate reference systems, datums, transformations — basis of EPSG.

ISO 19117 Portrayal How features are symbolized and rendered — feeds into OGC SLD / SE.
ISO 19123 Coverage geometry Abstract model for raster and field data — backbone for WCS and coverage APIs.

General (Non-Spatial) Data Standards

Table 5.2 — Enterprise Data Management ISO Standards / Enterprise ISO
Standard Title Role in Database Design
ISO/IEC 11179 Metadata registries The reference for building a controlled metadata registry — attribute definitions, value domains, data element governance.
ISO 8000 Data quality General-purpose data quality framework — accuracy, completeness, consistency, timeliness, provenance.

Non-Negotiable ISO 19115 metadata is not optional. A dataset without it is a file. A dataset with it is an asset. Every feature class you design should carry discovery, evaluation, and lineage metadata from day one — not "when we have time."

Pillar Four · Implementation

Esri Geodatabase Model

The Esri Geodatabase is not just a product — it's an opinionated implementation pattern for enterprise GIS. Even if you run on PostGIS or Oracle Spatial, the geodatabase concepts map directly to how professionals organize spatial databases.

The Core Geodatabase Objects

Fig 03 An enterprise geodatabase groups feature classes into feature datasets, enforces rules through topology and domains, connects tables via relationship classes, and supports concurrent editing through versioning.
Table 6.1 — Geodatabase Concepts and Their Purpose / Concepts
Concept What It Does When to Use
Feature Class A table with a geometry column + attributes. Every vector dataset — points, lines, polygons.
Feature Dataset A thematic folder holding feature classes that share a CRS. Group tightly related layers (all transport features, all utility features) that participate in the same topology.
Coded Value Domain Controlled list of allowed categorical values. Any attribute with a fixed vocabulary (road class, land use, status). Prevents free-text entry.
Range Domain Min / max validation for numeric attributes. Heights, speeds, counts, costs — anywhere out-of-range entries would be data errors.
Subtype Logical subclass of a feature class with different default values / rules. Roads table with subtypes Highway / Local / Residential — each with its own default speed limit and domain.
Topology Rule engine for spatial relationships (no gaps, no overlaps, must be covered by…). Parcel fabric, road network, administrative boundaries — anywhere spatial integrity is part of correctness.
Relationship Class Formal 1:1, 1:M, or M:N link between tables / feature classes, with referential integrity. Parcels ↔ Owners, Inspections ↔ Assets, Buildings ↔ Permits.
Attribute Rules (Arcade) Calculated, constraint, or validation rules executed by the geodatabase. Auto-populate fields, enforce business logic server-side without triggers.
Versioning Branch or traditional versioning for concurrent multi-user editing and history. Enterprise workflows with many editors — utilities, cadastre, asset management.
Beyond Esri Every one of these concepts has an equivalent in PostGIS (check constraints, foreign keys, triggers, table inheritance, PostgreSQL's logical/WAL-based versioning extensions). The Esri model is a useful mental shorthand — not a vendor lock-in.

Pillar Five · Modeling Language

UML & Data Modeling

Before any SQL is written, the model must be communicated. UML (Unified Modeling Language), maintained by the Object Management Group, is the lingua franca that domain experts, data architects, and developers use to agree on what the database must represent.

The ISO 19100 series is itself written in UML. INSPIRE data specifications are written in UML. Anyone who cannot read a class diagram is operating at a disadvantage in this field.

Fig 04 A simplified cadastral UML class diagram. Stereotypes (« featureType », « codeList ») mark spatial semantics. Multiplicities (1..*, 0..*) define cardinality. The diagram communicates the entire logical structure before any code is written.
Why It Matters A UML class diagram is the artifact that survives personnel turnover. Code and schemas drift. A well-drawn model remains the canonical source of truth that any new team member can learn the system from in one afternoon.

Method · The Design Process

Three-Tier Data Modeling

Good databases are not discovered — they are modeled. Every serious design moves deliberately through three tiers: Conceptual → Logical → Physical. Skipping a tier is the single most common source of expensive rework.

Fig 06 The three-tier progression from conceptual intent to running database. Each tier has a distinct audience, artifact, and question it answers.

What Each Tier Actually Produces

Table 9.1 — Tier Outputs Compared / Tier Outputs
Tier Primary Audience Artifacts Guiding Standards Done-When Criteria
CDM
Conceptual		 Domain experts, analysts, stakeholders UML class diagram, glossary, code-list catalog INSPIRE themes, UML, ISO 19109 (application schema) Every business entity has a class. Every business rule is expressed.
LDM
Logical		 Data architects, DBAs ER diagram, normalized table list, key definitions ISO 19107, 19108, 19111, 11179 Third normal form (unless intentionally denormalized). All relationships typed.
PDM
Physical		 Developers, DBAs, ops DDL scripts, index plan, topology rules, domains, migrations Esri GDB model, PostGIS, ISO/IEC 9075 (SQL) Schema deployed, indexed, with constraints, domains, and migration versioning in place.
Anti-Pattern Jumping straight to SQL. A database designed directly in DDL inherits every ad-hoc decision made under pressure. The CDM and LDM exist specifically to postpone those decisions until they can be made with full context.

Applied Design · The Five Building Blocks

Data Modeling in Practice

Theory is seductive; execution is what ships. This chapter is the bridge between the standards we've discussed and the two working projects that follow — an urban planning geodatabase and an agricultural geodatabase. Both are built from the same five construction elements.

Every enterprise geodatabase, regardless of domain, is assembled from five primitives: feature datasets group related layers, feature classes hold the features themselves, domains police the attribute values, subtypes introduce polymorphism inside a class, and relationships stitch everything together with referential integrity. Master these five, and you can design any spatial database.

Fig 08 The five building blocks of any enterprise geodatabase. Master these, and domain specifics become variations on a known theme.

The Five Blocks — In Depth

Block 01 · Feature Dataset

A feature dataset is a thematic container — a named folder that groups feature classes sharing a common theme and coordinate reference system. It is the unit at which topology is defined. In PostGIS the equivalent is a schema; in SQL Server Spatial, a schema plus CHECK constraints on SRID.

Design rule: only group feature classes into the same dataset if they genuinely participate in the same topology or share governance. Over-grouping creates contention; under-grouping means you cannot enforce spatial integrity between related layers.

Block 02 · Feature Class

A feature class is a relational table with a geometry column. It holds features of a single geometry type (point, line, or polygon) with a fixed attribute schema. Every feature class has a primary key, a spatial index on its geometry, and ideally at least one business-meaningful unique constraint.

Design rule: one geometry type per feature class. Do not mix points and polygons in a single class "for convenience" — queries, symbology, and topology all break.

Block 03 · Domain (Coded Value & Range)

A domain is a reusable rule attached to an attribute that constrains what values are legal. Coded value domains hold controlled vocabularies (RSD COM IND); range domains enforce numeric bounds (heights 0–500 m). Domains apply at the database level — the application does not need to know about them for the rule to be enforced.

Design rule: every categorical attribute gets a coded value domain. Every numeric attribute with known bounds gets a range domain. No exceptions.

Block 04 · Subtype

A subtype is a logical subclass within a feature class, distinguished by a single discriminator field. Subtypes share a schema but can carry different default values, default symbology, different domains on the same field, and different attribute rules. The classic example is a Roads feature class with subtypes Highway, Arterial, Collector, Local — each with its own default speed limit and surface type.

Design rule: use a subtype when the variations genuinely share a geometry and most attributes but differ in behavior or defaults. When the variations differ in more than half their attributes, make them separate feature classes instead.

Block 05 · Relationship Class

A relationship class is a formal link between two tables or feature classes, with cardinality (1:1, 1:M, M:N), notification direction, and deletion behavior. A simple relationship preserves orphans on deletion; a composite relationship cascades — deleting a parcel deletes its building attachments, for instance. In PostGIS this maps to foreign keys with ON DELETE CASCADE or RESTRICT.

Design rule: prefer composite relationships when the child cannot exist without the parent (a permit without a parcel is nonsense). Prefer simple relationships when the child is independently meaningful.

Table 11.1 — The Five Blocks at a Glance / Summary
Block Purpose Esri Term PostGIS / SQL Equivalent
Feature Dataset Thematic grouping & topology scope Feature Dataset PostgreSQL schema + SRID constraint + topology schema
Feature Class Typed geometry + attributes Point / Line / Polygon FC Table with a geometry(TYPE, SRID) column + GIST index
Domain Attribute value constraint Coded Value / Range Domain CHECK constraint or FK to a lookup table
Subtype Logical subclass within one FC Subtype on a field Discriminator column + CHECK + partial indexes / triggers
Relationship Referential integrity between FCs/tables Relationship Class (simple/composite) FK with ON DELETE CASCADE / RESTRICT
Pattern to Internalize Model, constrain, relate. First model the shape (feature datasets and classes). Then constrain the values (domains and subtypes). Finally relate the entities (relationship classes). Doing them in that order prevents most design dead-ends.

Roads Must Not Have Dangles (with exceptions) Road segments should connect to the network; dead-ends flagged for review.
Roads → Intersections Endpoint Must Be Covered By Every road endpoint must coincide with an intersection point.

The Temporal Dimension

Agriculture is time-series data by nature. The schema treats time as a first-class concept through three mechanisms:

(1) Valid-time columns — every crop plot carries planting_date and harvest_date; every sensor reading carries observed_at. (2) Season foreign key — every planting ties to a Seasons lookup so "Summer 2025" is a single canonical identifier, not a free-text field. (3) Time-series partitioning — sensor observations are stored in a separate time-series table partitioned by month, not as attributes on the sensor feature class itself.

CropPlots — DDL with Temporal & Subtypes PostgreSQL / PostGIS 
-- CropPlots feature class: temporal, subtyped, cascading relationships
CREATE TABLE agri.crop_plots (
    plot_id         BIGSERIAL PRIMARY KEY,
    field_id        BIGINT NOT NULL
                    REFERENCES agri.fields(field_id) ON DELETE CASCADE,
    season_id       INT NOT NULL REFERENCES agri.seasons(season_id),
    crop_type       TEXT NOT NULL
                    CHECK (crop_type IN
                        ('WHEAT','RICE','CORN','BARLEY','COTTON','SUGARCANE',
                         'SORGHUM','SOYBEAN','POTATO','TOMATO','ONION',
                         'ALFALFA','CITRUS','OLIVE','DATE_PALM','FALLOW')),
    crop_category   TEXT NOT NULL         -- subtype discriminator
                    CHECK (crop_category IN
                        ('CEREAL','LEGUME','FRUIT','VEGETABLE','FODDER',
                         'OILSEED','FIBER','INDUSTRIAL')),
    variety         TEXT,
    planting_date   DATE NOT NULL,
    harvest_date    DATE,
    irrig_method    TEXT CHECK (irrig_method IN
                        ('DRIP','SPRINKLER','FLOOD','FURROW','PIVOT',
                         'MICRO_SPRAY','SUB_SURFACE','RAIN_FED')),
    area_ha         NUMERIC(10,3) CHECK (area_ha > 0),
    geom            geometry(MultiPolygon, 32636) NOT NULL,
    -- temporal uniqueness: one crop per field per season
    UNIQUE (field_id, season_id, geom)
);

CREATE INDEX idx_plots_geom    ON agri.crop_plots USING GIST(geom);
CREATE INDEX idx_plots_field   ON agri.crop_plots(field_id);
CREATE INDEX idx_plots_season  ON agri.crop_plots(season_id, crop_type);
CREATE INDEX idx_plots_dates   ON agri.crop_plots(planting_date, harvest_date);

-- Typical temporal query: yield per crop per season for a region
SELECT s.season_name, p.crop_type,
       SUM(p.area_ha) AS total_ha,
       AVG(y.yield_value) AS avg_yield_tha
FROM agri.crop_plots p
JOIN agri.seasons s ON p.season_id = s.season_id
LEFT JOIN agri.yield_points y ON y.plot_id = p.plot_id
WHERE s.season_year = 2025
GROUP BY s.season_name, p.crop_type
ORDER BY total_ha DESC;

Professional Delivery Advice

Everything above defines the schema. The following practices make the delivery professional — the difference between "a database that exists" and "a database that a serious client will trust, pay for, and renew."

ADVICE · 01
Adopt a clear naming convention
PascalCase for feature class names (CropPlots), snake_case for fields (planting_date), ALL_CAPS for domain codes (DRIP). Prefixes for datasets (fd_), domains (dm_), and lookup tables (lu_) make the schema self-describing.
ADVICE · 02
Never deliver without a data dictionary
Generate the data dictionary directly from the schema — never by hand. Every feature class, every field, every domain must appear with type, constraint, definition, and source. A client who asks "what does this field mean" should never hear "let me get back to you."
ADVICE · 03
Ship INSPIRE-style metadata per dataset
Every feature class carries an ISO 19115 metadata record: title, abstract, spatial resolution, CRS, lineage, accuracy, constraints, point of contact. Store metadata in a dedicated table or catalog; render it in reports automatically.
ADVICE · 04
Automate QA/QC as a pipeline
Run geometry validity, topology conformance, domain conformance, and referential integrity checks as a scheduled CI job — not a pre-delivery ritual. A failing check blocks promotion to production. Manual QA is skipped under deadline pressure; automated QA is not.
ADVICE · 05
Version the schema like source code
Use Liquibase or Flyway. Every change to a feature class, a domain, or a relationship is a reviewed, tested, reversible migration. Dev, staging, and production environments apply the same ordered list of migrations — no drift, no surprises.
ADVICE · 06
Index for the queries you actually run
Every geometry column gets a GIST index. Every foreign key gets a B-tree index. Every attribute that appears in a WHERE clause of a frequent query gets an index. Measure with EXPLAIN ANALYZE — do not guess.
ADVICE · 07
Separate read and write workloads
Editors hit an OLTP database with short transactions. Analysts and dashboards hit a read replica or materialized analytical schema refreshed nightly. One workload never blocks the other; queries don't fight over locks.
ADVICE · 08
Document the lineage of every dataset
Where did it come from? How was it captured? What transformations were applied? What is its accuracy and vintage? A dataset without lineage is a liability — someone will use it for a decision it cannot support.
ADVICE · 09
Publish through standard OGC services
Expose every feature class through OGC API – Features (or WFS for legacy). Rasters through OGC API – Coverages and COG. Metadata through CSW or OGC API – Records. Standards-based publishing removes the integration cost for every downstream consumer.
ADVICE · 10
Design for handoff from day one
Write the handoff document as you design, not after. How to restore from backup, how to run QA, how to publish, how to add a new domain value, how to roll back a migration. A project that depends on one person's memory is not delivered — it is rented.
Final Principle Design the database like you will have to defend it in an audit. Because eventually, you will. Every constraint, every domain, every relationship has a reason — and that reason should be written down, traceable, and reviewable. That discipline is what separates professional GIS delivery from hobbyist output.

Operational Rules · What Works

Best Practices & Checklists

What follows is not theory. It is distilled from projects that succeeded and others that failed expensively. Use these as a gate review checklist before any database moves from development into production.

Mandatory Practices — No Exceptions
Level 01 / Baseline conformance
Ship ISO 19115 metadata with every dataset from day one. Title, abstract, lineage, constraints, point of contact. No metadata, no production.
Align every spatial feature class to an INSPIRE theme — even if compliance is not required. The thematic discipline alone is worth it.
Publish through OGC-compliant services (OGC API preferred; WMS/WFS for legacy compatibility). Never ship as raw file downloads only.
Enforce coded value domains on every categorical attribute. A TEXT column with no vocabulary is a future cleanup project.
Define topology rules for datasets where spatial integrity is part of correctness — parcels, roads, admin boundaries, utility networks.
Use relationship classes with referential integrity — never rely on "the application will handle it."
Specify coordinate reference systems explicitly — never assume, never default. Record the EPSG code in metadata and in every geometry column.
Run topology + quality validation as a CI step, not a manual pre-delivery ritual.
Advanced Practices — Mature Organizations
Level 02 / Enterprise-grade
Separate operational from analytical stores. OLTP for editing, OLAP/warehouse for analytics. Mixing them guarantees one use case will degrade the other.
Add a temporal dimension — valid-time and transaction-time columns — for any dataset where "as-of" queries have business value (cadastre, asset history, land use change).
Version your schemas like code. Use Liquibase or Flyway. Every change is a migration, reviewed and reversible.
Build a metadata registry (ISO 11179). Every attribute is defined once and referenced by all consumers.
Instrument data quality (ISO 19157 / 8000). Completeness, accuracy, consistency — measured, scored, trended over time.
Use GeoParquet or Cloud Optimized GeoTIFF for large analytical workloads — not Shapefile, not plain GeoTIFF.
Apply ISO 27001 controls — role-based access, audit logs, encryption at rest and in transit. Security is not a feature; it is a property.
Document data lineage — not just sources, but every transformation and decision. Six months from now, you will need this.

What Not to Do · Anti-Patterns

Common Pitfalls

Every pattern below has been observed repeatedly in the field. Most are cheap to fix early and expensive to fix late.

“
The most dangerous database is the one you trust too much. Its errors are invisible until they cost you.
— Senior Practitioner Axiom
i
Designing schema without standardsFail at first integration
Symptom: Custom attribute names, home-grown code lists, bespoke geometries. Fix: Start every new schema from the closest INSPIRE theme and ISO 19107 geometry model. Extend — never replace — the standard vocabulary.
ii
Treating metadata as paperworkData unusable downstream
Symptom: Metadata filled in days before audit, copied between datasets, outdated within a month. Fix: Generate metadata from the schema and pipelines automatically. Manual metadata is always wrong within one release cycle.
iii
Free-text where a domain belongsGarbage attribute values
Symptom: Res. RESIDENTIAL res Residentiel all in the same column. Fix: Any categorical attribute gets a coded value domain at design time. Cleanup is ten times more expensive than prevention.
iv
Mixing CRSs silentlySpatial joins return nothing or wrong results
Symptom: Layers appear misaligned; spatial queries produce absurd distances or empty joins. Fix: Enforce a project CRS. Store EPSG code on every geometry column. Reject imports that don't declare a CRS.
v
One giant feature class for everythingUnindexable, slow, unworkable
Symptom: "All assets" table with 80 nullable columns, subtype controlled by a single discriminator. Fix: Split into feature classes per logical type with shared relationship classes. Use subtypes only where they actually reduce complexity.
vi
Shapefile in production workflowsTruncated names, 2GB limit, no dates
Symptom: Field names truncated to ten characters, attribute types coerced, 2 GB ceiling hit under load. Fix: Use GeoPackage for file delivery, PostGIS or enterprise GDB for workflows. Shapefile is legacy delivery format only.
vii
Skipping topology until after loadSilent data corruption
Symptom: Parcels overlap slightly; network edges don't snap; polygon boundaries have microscopic gaps. Fix: Define topology rules before loading. Run validation as part of every ingest. Block bad geometries at the gate.
viii
No indexing on geometry columnsMinute-long queries that should take milliseconds
Symptom: Dashboard backends crawl under moderate load. Fix: Build a GIST (PostGIS) or spatial index (GDB) on every geometry column. Rebuild after bulk loads. CREATE INDEX idx_geom ON table USING GIST(geom);
ix
No separation of operational and analytical storesOne workload starves the other
Symptom: Long analytical queries lock out editors; batch jobs collide with interactive users. Fix: Separate OLTP (editing) from OLAP (analytical) with scheduled replication. Simple rule with large payoff.
x
Versioning database schemas ad-hocDev / staging / prod drift
Symptom: Migrations applied manually, sometimes forgotten. Production differs from staging in ways nobody can enumerate. Fix: Liquibase or Flyway. Every schema change is a reviewed, tested, reversible migration.
